## Stable local invariants

For a project that declares GitHub as its Software system of record, current remote
GitHub refs, Issues and PRs are the development authority. Agent/Owner local
checkouts are temporary execution workspaces, not hidden unfinished project
state. Prefer a direct GitHub connector or authorized native Git; a remote
computer is used only for genuinely local-runtime/device/deployment work.
Publish changes before claiming completion and clean up only scratch that
the current agent created. Preserve pre-existing user files and approved
domain/Canon authorities. Reuse configured environments; missing required
setup is reported through existing Liaison/Control, never auto-provisioned.


Describe **only** genuine persistent product/domain/security/Canon requirements here.
Preserve local privacy, tenant, auth, money, data ownership, licensing and other
approved restrictions. They may be stricter than general Software habits;
never weaken an Owner/Canon or security boundary to simplify this profile.

## Conditional local workspace

## Entry and continuation

- **Cold:** read this root file at the exact selected project ref, resolve current task and declared product/Canon authority, then load only needed Resolver/role/workflow/skill instructions. A linked sibling repository is not implicitly inherited or necessarily accessible.
- **Warm, same live agent instance and same admitted role:** reuse already-present unchanged relevant instructions. Revalidate current task, exact GitHub target/HEAD, affected authorities and mandatory evidence, not every document or skill again.
- **Fresh independent agent instance:** do not presume predecessor memory. Receive essential scoped clauses and exact source refs through the existing governed Assignment/Handoff, then load missing or changed selected instructions only.
- **Invalidation:** reload affected instruction/Canon/role/skill sources when they change materially or are absent; do not invalidate unrelated sources just because a non-governing file changed.
- **Capability and acceptance:** prove actual destination capabilities and action authority separately. `AGENTS_PRESENT` is not `ENTRY_VALIDATED`; neither is `PROJECT_ROUTABLE`, `ASSIGNMENT_ADMISSIBLE` or `OUTCOME_ACCEPTED`. An entry marker is not automatic project acceptance.

## Scope of this template

This is a **portable example**, not a published parser/automatic validator or
a reason to introduce new agent roles, runtime, transport, permanent per-task
Markdown reports, test suites or CI gates. Preserve existing project-specific
AGENTS rules until a bounded, independently reviewed migration proves they are
redundant or obsolete. Do not include live SHAs, Issue numbers, status logs or
provider credentials in the permanent profile.
