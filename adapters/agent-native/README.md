# Agent-native Resolver adapter — Stage 1

Purpose: use ChatGPT Work/Chat for Liaison and Control; delegate GitHub-backed
Software execution to a **distinct native Work Subagent**, Codex Cloud
Executor or another admitted capable agent; and verify independently when
required. Manual Chat/Codespaces remain separately selected alternatives, not
retired-transport fallbacks. No new runtime, MCP, Director or role is introduced.

This adapter is a **bounded entry method**, not a provider API or dispatch
implementation. Existing BOOTSTRAP.md, ROUTER.md, selected Engine/Workflow/Role,
ASSIGNMENT_COMPILATION_CONTRACT, EXECUTABILITY_CONTRACT and Verification own
all semantic authority.

## Portable target AGENTS.md entry (v1)

The root `AGENTS.md` of an **opted-in** product can use the short, human- and
agent-readable `project-resolver:entry-v1` profile in
[`AGENTS.example.md`](AGENTS.example.md). Its project/Resolver locators,
product authority and conditional references are navigation data only. They
do not inherit the Resolver from a sibling checkout or authorize a remote
agent, merge, deployment or Canon decision.

On a **fresh** role entry, load relevant instructions once and prove actual
host/tools and current target. In the **same live instance and admitted role**,
reuse unchanged loaded instruction context while revalidating the exact task,
HEAD and affected sources. A **new** instance reconstructs only its necessary
instructions from an actual Assignment/Handoff; do not claim hidden-memory
continuity. See `BOOTSTRAP.md` and existing Context Continuity / Handoff semantics. No new
runtime/session cache or automatic project-acceptance claim is introduced.

## Host profiles and agent lifecycle

Host and instance admissibility is owned by `roles/MANIFEST.yaml` and the host boundary in `AGENTS.md`. Follow `AGENTS.md` for first launch, known-session reuse and recovery, and `kernel/skills/anti-loop-execution/SKILL.md` for the scope of a STOP.

## Stage 1 role mobility and economical interface choice
- One ordinary Chat session may handle Liaison discussion and then governed Control Director coordination in bounded phases, returning to the Owner-facing projection without a permanent separate Liaison. Its Director authority still comes from existing router/admission/control contracts, not the chat or role label.
- For approved Work-native Software, the Director may select distinct **Work Subagent Executor** or Codex Cloud Executor based on actual available tasks and publishing permissions; do not force a provider merely because an older profile preferred it. Honor a specifically frozen in-flight route. Never substitute Linear `@codex`, PR-comment coding commands, disconnected legacy Codex or hidden Chrome. Separately selected manual Chat coordination remains valid.
- Director delegates **every** Software implementation/microfix/repair to an admitted Executor/subagent. A single Codex Executor may do audit then implementation **only** after durable audit results, approved scope and a fresh admitted assignment; this is task reuse, not promotion to Director or Verifier.
- A Director who did not implement the candidate may conduct the full V1–V4 review. A specific requirement for another assessor still needs a distinct actual Verifier; neither reused conversation memory nor produced_by_role metadata proves that independence.
- Executor never merges. After mandatory evidence/verification and authority reconciliation, only Director/Control initiates an authorized promotion/merge; external automation is used solely when proven available.
- Agent instance reuse is optional, not required for continuity. Persist the active control baton and exact refs so a new manual session can resume per #7.

For manual chat-to-chat handoffs, assignments, and agent prompts, follow the
presentation rule and its two-unit Workflow Director exception in `AGENTS.md` and
`protocols/skills/session-handoff/SKILL.md`. Persist required artifacts in the
declared system of record and carry exact references into the message.
Native GitHub-bound implementation and independent verification have been
demonstrated in bounded flows. Work Subagent admission now allows distinct
Work-native Executors, but this statement does not claim that every host can
launch them, that every subagent can publish, or that unattended scheduling
and wakeups have been verified.

## Optional local-runtime proof (never a default dispatch)

Use a checkout only when an admitted task genuinely requires shell, language
runtime or local-state evidence. Do not provision sibling repos or inspect the
Owner's workstation for ordinary GitHub review/implementation.

1. Select the target and Resolver's exact GitHub refs remotely.
2. Reuse a permitted isolated local worktree only when needed; protect user data.
3. Existing `tools/agent_native_preflight.py` may prove local SHA identity,
   but `LOCAL_STATE_MATCH` is not remote freshness, dispatch or publication.
4. Publish via the selected GitHub route; Control reads the remote PR/HEAD.
   Remove only agent-owned temporary files after durable publication.

## Work / Chat without a checkout shell

Read the target's authoritative GitHub refs via an authorized connector.
Apply the same semantics with the current real capability profile; do not run or
claim this local shell preflight. If the selected tool cannot submit/observe a
Codex task or another ChatGPT tab, do not claim dispatch. Use an actually
supported native/manual handoff or state the bounded limitation.

## Transport and resource boundary

Use existing Resource Governance for selected metered operations. Native
Codex/GitHub code delivery is demonstrated; this optional adapter does not
supply unattended scheduling or browser wakeup. Retired Linear or remote-less
Codex routes must not be selected as fallback. Report the exact unavailable
native operation rather than trying legacy execution.
