# Project Resolver Agent Rules

This repository is the **Project Resolver / Agent Project Operating System**. It is a modular monorepo of bounded engines, shared contracts, durable roles, protocols, skills, and evidence rules.

**Current status / navigation:** Read current GitHub `main`, repository contracts, and applicable project-specific authority. Private governance Issues are not distributed with this public source snapshot. Old snapshots, archives, superseded comments and retired transport experiments are historical provenance, **not active dispatch instructions**. Native Codex/GitHub publication is already proven for bounded flows; a background scheduler is not claimed.

## Strategy 2030

Apply `kernel/STRATEGY_2030.md` to product foundations, architecture and Software planning/delivery. Domain capabilities are primary; all interfaces are secondary projections/adapters. MCP capabilities may lead UI. AI-search visibility and HTML projections are required for discoverable public product information; A2A implementation is required for applicable agent-enabled products. Preserve bounded assignment scope, actual deployment evidence and existing authority/security rules. Reuse existing site-to-agent approaches before claiming a gap or creating the conditionally requested separate protocol project.

## Selected native transport: no legacy dispatch or hidden-browser fallback

For a GitHub Software assignment, preserve the actually selected and admitted execution route, repository, candidate owner and any Owner-selected visible control. **Native Work Director → distinct Work Subagent Executor → GitHub** and **Work/Chat Director → Codex Cloud Executor → GitHub** are both permitted routes. The Director does not implement its own governed change; it may fully review a separate Executor's exact candidate at V1–V4 unless a specific requirement needs another assessor. A previously frozen Codex route must not be silently rewritten mid-assignment; new authorized work may use whichever proven Work-native executor is suitable. Mere tool discoverability does not authorize an unproven action or retired provider.

**Retired for implementation and repair dispatch on an approved native route:** Linear agent delegation or Linear `@codex` issue transport, PR-comment `@codex address that feedback` as a replacement Executor, and legacy Codex environments without the selected GitHub repository's remote/publishing access. Do not retry these even when they appear connected. An agent's claimed local commit is not GitHub PR publication. Other provider routes are possible only if separately authorized and admitted.

If the native route cannot publish the actual PR/HEAD, preserve the attempt and return the exact WAIT/ESCALATE error. Do not launch another Executor, install/provision an alternate environment, send source code through chat or recover via old transport.

If the Owner selected **visible Desktop-integrated Codex browser MCP**, do not open hidden Chrome tabs, background browsers or a separate Work cloud browser instead. Report unavailable visible controls rather than substituting them. For normal GitHub source, PR, Issue and CI operations use GitHub Connector directly without browser navigation.

## Executor lifecycle: first launch is not a reuse failure

For a **new** authorized workstream with no previously dispatched Executor/active Assignment, Director must **start a new Executor through the already-approved native agent facility** when that action is actually available. Finding no previous agent, chat, task or GitHub result is the expected cold-start state, **not** a reason for `WAIT`, `ESCALATE`, a new Owner gate or another transport preflight. Launching a bounded agent instance in an existing configured environment is not provisioning a new account, repository, machine, worker service or other persistent infrastructure. Do not scan unrelated historical chats for a worker that this workstream has never created.

For a **continuing** Assignment, prefer reuse of the specifically identified live Executor when it still has the required role/capabilities; reuse is an optimization, never a prerequisite. A different separately admitted Assignment may use a fresh Executor without resurrecting retired dispatch or manufacturing an environment.

For **recovery**, first reconcile a known in-flight/uncertain-ack attempt and the exact remote GitHub candidate. Absence of a GitHub commit alone does not prove that a dispatched agent never started. Do not duplicate an unresolved attempt. If the prior task is demonstrably finished/failed/unavailable with no surviving unpublished work, create a newly admitted Executor via the same approved native route, using the existing Issue/PR and durable handoff. Retain completed steps and independent verification requirements.

A two-error/anti-loop STOP suspends the **specific failing operation or correction stream**, not every independent already-authorized stage. Whole-workstream `COMPLETE` requires the final Owner outcome; a real non-executable dependency can remain in `WAIT/ESCALATE` with the durable control baton intact. No rule promises unattended wakeups after the controlling session ends.

## Stage 1 host/role boundary (Owner-approved, #4/#12)
Identify the **actual host product/surface** from trusted launch or tool context **before** choosing a role; `SBC_RUNTIME_CONTEXT` and `ORDINARY_CHAT` describe transport/bootstrap, not ChatGPT-versus-Codex identity. A self-declared role, guessed environment, presence of a shell, or absence of SBC context is not host proof. Apply the matching documented policy in `roles/MANIFEST.yaml`:

- **Codex Cloud:** `executor` only, including read-only diagnosis, audit and subsequent implementation under separate Assignments. Do **not** bootstrap as Liaison, take over Director/Owner-facing control, create an independent `VERIFICATION_RESULT`, approve or merge your own PR. Report evidence and hand off to Control.
- **ChatGPT Work Director (parent instance):** `owner-interface`, `control-director`, or separately admitted `control-verifier`; **not Executor for its own controlled work**. Delegate implementation/microfixes to a distinct native Work Subagent, Codex Cloud Executor or another separately admitted worker. A genuinely separate Work Subagent may be `executor` when the selected host exposes that action, assignment scope and GitHub publication capability. Another distinct Work Subagent may verify a candidate only when it did not implement it and can independently read the required evidence.
- **ChatGPT Chat:** may be admitted to any shared role **for which it has authority and actual capabilities**. One instance may perform Liaison/Director sequentially, but not Director and Executor of its own governed assignment; independent verification requires a different instance from the candidate's Executor. "Any role" does not mean simultaneous incompatible roles.
- **Unidentified host:** do not infer elevated or incompatible privileges. Obtain actual host binding / choose a proven admissible destination or report the limitation; do not pretend to be ChatGPT Chat merely because `SBC_RUNTIME_CONTEXT` is absent.

These are currently **agent-facing role entry rules**, not proof that host-bound platform attestations or automated role gating have been implemented. No permanent agent/transport, new role, or Stage 2 scheduler is introduced.


## Local-computer workspace
When a task actually uses a user's computer, before substantive shell actions or project writes load `kernel/skills/local-workspace-operation/SKILL.md`, resolve the user's local workspace profile and read any configured instruction source and applicable host/user rules. Prefer direct file/host reads; a minimal read-only shell bootstrap is permitted only when a required direct bootstrap step is unsupported by the surface (including genuinely unresolved home) and applicable user/host rules allow it, never to bypass a denial. Carry the profile reference and applicable constraints to the actor doing that work. Set the task's real working directory and honor its selected shell; do not treat a terminal/server startup directory as a project root. Remote-only tasks do not require local setup. These are agent instructions, not an OS sandbox.

## Evidence-backed constraints and complete deletion

Treat claimed product, provider and runtime limits as facts only when supported by current Owner decisions, applicable contracts, relevant official documentation or direct observation. Keep unresolved assumptions explicit; a necessary implementation default or safeguard is a design choice, not an invented provider rule. Existing code, configuration or tests show what is implemented, but do not alone prove continuing authority or necessity. Preserve actual approved requirements and protected security/data boundaries; do not add speculative restrictions, tests or Owner gates.

When an authorized change removes or replaces an element, remove in-scope checks, scripts, configuration and CI steps whose only purpose is that retired element, including assertions that it is absent. An optional one-off absence check is temporary: remove it immediately after its first successful result, before handing off the candidate. Keep checks of current behavior and active requirements; do not turn this rule into a new audit or verification gate.

## Mutable working assets and scoped integrity

Ordinary working files are replaceable by default, whether text or binary (for example images, audio, video, fonts, and other static product content). An authorized replacement, resize, recompression, or optimization is a normal source/content update through the existing Git or object-storage and deployment path. Preserve a required public URL or mapping where applicable, not the old file bytes; stable paths are not immutable-content promises. The identity of a particular Git revision does not make its assets immutable across future revisions.

Use hashes, signatures, pinned manifests, or immutable snapshots to protect only a **specifically established integrity or compatibility boundary**: for example an archival/migration evidence copy, a signed/security-sensitive artifact, an independently versioned incompatible data release, or another explicit applicable requirement. A historical digest proves the inspected snapshot's bytes, not the perpetual identity of a live file. Keep archival verification separate from routine builds. Do not introduce build-breaking comparisons against historical hashes, mandatory external archives, asset-registration workflows, or approvals merely to change ordinary product assets. The optional `immutable-deployment-data-pinning` pattern does not apply without its actual code/data compatibility assumptions. Preserve real security/integrity protections where they are required; do not invent new gates or tests.

## Default GitHub-first posture for GitHub-backed Software work

When GitHub is the declared source of truth for a Software project, the **remote repository**, current Issue/PR, pushed branch, exact commit HEAD and applicable remote CI/result records are authoritative for development. An Owner workstation, agent sandbox, local clone or unpushed commit is an **ephemeral execution surface**, not a second backlog or hidden project state. Do not block remote-governed work to investigate unrelated stale/dirty local checkouts or claim local leftovers are unfinished project work. If the specific selected local worktree is dirty and needed for a mandatory operation, preserve existing edits and use an authorized clean isolated worktree or stop that local operation; never overwrite or delete user-owned files.

For GitHub reads/writes, use the connected GitHub Connector/API or the Executor's authorized native Git/GitHub path; a distinct Work Subagent or Codex Executor normally publishes its own assigned branch and Draft PR. Remote Desktop Commander or any machine bridge is exceptional: use only when a real local file, installed CLI/runtime, application/device check or deployment operation **requires that machine** and no suitable direct provider path exists. Connection or available shell access does not justify using it for routine repository/PR/CI operations. Reuse current exact-HEAD evidence and do not rerun equivalent checks without a concrete reason. If the target repository's active rules prohibit remote-computer access entirely, that stricter restriction overrides this conditional generic allowance.

Reuse **existing, configured** target repository, access, Codex environment or other admitted execution destination. For a real Software assignment, identify the exact target and necessary destination capabilities from current evidence before dispatch, not by repeated generic probes. Missing required setup is an explicit actionable capability limitation, **not** permission to create repositories, accounts, environments, Codespaces, services or installations. Route a genuinely required Owner setup step through Liaison; Control retains WAIT/ESCALATE when no admissible route exists. Do not invent an Owner gate for an already available setup.

Publish authorized code/results to the declared durable remote source before completion. Keep unavoidable local work isolated and temporary; after proven durable publication clean up **only agent-created** scratch/worktrees and leave pre-existing/user-protected data untouched. A local-only result is not a published GitHub candidate. These rules apply to Liaison, Director, Executor and Verifier without replacing authority, verification or necessary local-runtime evidence. See `contracts/EXECUTABILITY_CONTRACT.md` and the selected Software workflow.

## A missing GitHub CLI is not missing GitHub access

A failed local `gh` command (including `gh: command not found`) proves only that **one CLI method** is unavailable. It does not invalidate the currently connected GitHub Connector/API, GitHub repository permissions, or the rest of the approved Work flow. For GitHub Issues, PRs, diffs, CI and similar provider operations, use the already working GitHub Connector/API for the same authorized action. The `gh` executable is optional, not a global precondition.

Changing a tool method within the **same authorized GitHub provider, repository and operation** is not replacing the chosen Codex Executor, physical transport, or Owner-selected visible UI. Reuse previously observed actions as evidence only within their actual permission/scope and freshness. If one method fails, use another already admitted method without new Owner gates or environment setup. If no method can complete a genuinely mandatory operation, block only dependent work and preserve the baton for other authorized tasks.

Never install `gh` solely to restore already working GitHub access, resurrect legacy Linear/Codex dispatch, or open hidden browser sessions as an improvised fallback.

## Git-first delivery must survive every execution handoff

For an approved GitHub code change, **a temporary local checkout is only a work surface, never the durable result**. Before substantial edits, the admitted publisher must have an actually proven path to the selected remote branch/PR; tools capable only of Issue comments or local commits do not prove code publication. Reuse the existing candidate/branch. A claim that source was changed or locally tested is not a GitHub commit.

Before an Executor yields a substantive work turn, terminates its workspace, rotates session context or reports completion, it must publish all intended work to the existing authorized remote candidate and provide its **actual GitHub HEAD**. Incomplete work and red checks may be preserved in that **same Draft PR** as explicitly WIP, not declared accepted. Do not delete the only working copy after a failed publish. If publication truly fails, report exact `PARTIAL/BLOCKED` and preserve the original attempt; a local patch or chat report is not a durable checkpoint.

Control independently reads the real remote candidate **after each Executor return**. A missing/unadvanced HEAD is a still-open publishing obligation, not completion, and it is not permission to start another Executor, switch to a retired transport, assign new work to the same uncommitted state or ask the Owner whether to continue a previously approved task. Preserve the baton and original work until the publishing path is reconciled. Follow the existing anti-loop STOP for genuine repeated technical failures, but never equate STOP with permission to discard unpublished work.

## Chat output and manual handoff presentation

Presentation follows the delivery channel, regardless of the receiving role or host, including a browser-based Control Director, Executor, or Verifier.

- **Ordinary chat response:** answer directly in chat. Never deliver a generated `.md` file or Markdown document attachment as a substitute for the response.
- **Manual chat-to-chat handoff, assignment, or agent prompt:** normally output exactly one flat, directly copyable plain-text block containing the complete manual message. Use plain-text labels and references; no nested code fences, file wrappers, attachments, or downloads. Exception: every Owner-facing / LSO Director handoff of an approved workflow to a separate Workflow Director uses exactly two independently copyable text units: the complete workflow assignment, followed by the fixed short launch instruction in `protocols/skills/session-handoff/SKILL.md`. The Owner pastes both into the same outgoing message.
- **Durable project artifact:** persist the actual artifact in the authorized repository, Google Drive, or other declared system of record. Return exact references and a concise human-readable summary in chat. A chat message or attachment does not replace required durable publication or readback.

These presentation rules preserve existing artifact schemas, authority boundaries, durable readback requirements, and handoff semantics. They introduce no role or transport and do not establish dispatch, receipt, verification, or completion.

## Control rules

- **State is durable. Chat is not authoritative state.** Use explicit artifacts and exact state references.
- **Agents are disposable; roles are durable.** An active agent instance is assembled from relevant state + engine + workflow + role + destination capability profile + assignment admissibility proof + assignment + required skills.
- **Context is assembled, not inherited.** Do not rely on hidden or prior chat history as authority.
- **Engine authority is bounded.** An engine owns its declared work class only. Software does not own K0/Owner authority, Canon truth, Research truth, or universal contracts.
- **Semantic capability != executable capability.** Engine/workflow selection does not imply that the selected destination has checkout, shell, language runtime, browser, database, deployment, network, CI, or connector access.
- **NO ASSIGNMENT WITHOUT EXECUTABILITY PROOF.** Before `ASSIGN`, derive all capabilities required by mandatory actions and mandatory evidence/acceptance gates, bind an exact destination `CAPABILITY_PROFILE`, and prove `REQUIRED_CAPABILITIES ⊆ AVAILABLE_CAPABILITIES` under `contracts/EXECUTABILITY_CONTRACT.md`.
- If required capabilities are not proven, return `ASSIGNMENT_NOT_ADMISSIBLE` or choose another already-authorized executable destination/mode. Do not intentionally send impossible work downstream just to receive `BLOCKED`.
- **Default Research is machine-only.** Owner/K0 is the only default human actor and supplies project authority, not routine research labor. New third-party human research is invalid unless Owner/K0 explicitly creates a separate bounded `human-research/` workstream.
- Load only the selected engine manifest and its declared dependencies. Do not cross an engine boundary by convenience.
- Follow the exact assignment and its authority. No silent scope expansion, no silent Owner-intent redefinition, and no silent state mutation.
- Claims that depend on a candidate/revision/environment must cite exact-state evidence. `ARTIFACT != EVIDENCE`; evidence must actually support the claim.
- Missing capability discovered after a previously valid assignment is `BLOCKED_RUNTIME_DRIFT`; missing capability known before assignment is an admissibility failure, not ordinary Executor work.
- Missing authority, unresolved contradiction, unavailable required engine, or absent mandatory evidence path is an explicit stop/escalation condition, not permission to improvise governance.
- **Solution Patterns are optional.** Select them only when their assumptions, rejection conditions, and execution prerequisites match; production success never promotes a pattern into universal law.
- Relevant shared-state change invalidates affected evidence/preconditions until fresh verification, equivalence proof, rebuild/rebase, or explicit stop. A universal exclusive lease is not required.
- Architecture is not reconsidered merely because implementation is difficult. Distinguish implementation failure, local architecture defect, and invalidated architecture assumption; open an Architecture Reconsideration Gate only on evidence or before an explicitly planned hard-to-reverse commitment.

## Durable control

State changes require explicit authority and a durable mutation/decision record. Role-native outputs remain distinct: a Director's own `DIRECTOR_REVIEW` is recorded in its decision; a separately selected Verifier produces its own `VERIFICATION_RESULT`, alongside the `EXECUTOR_RESULT`.
