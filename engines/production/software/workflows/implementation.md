# Software Workflow — Implementation

**Entry:** an exact software assignment with authority, relevant state, and destination executability proof. `execution_contract.proof_status` must be `PROVEN` for the exact destination/execution mode before the Executor is activated.

**Strategy:** apply `kernel/STRATEGY_2030.md` to affected product architecture and delivery: capabilities first, interfaces secondary, MCP may lead UI, required public AI-search/HTML projections and applicable A2A implementation. Record actual rollout/evidence in the existing plan/result; a bounded repair or policy edit does not implicitly deploy adapters.

**Primary role:** `roles/executor/ROLE.md`.

Load by need, not all at once:
- planning: `skills/implementation-planning`;
- MCP design/integration: `skills/mcp-adapter-intake` when actually requested; select its four neighboring MCP skills only for the specific contract, auth, coverage or acceptance question;
- independent agent-to-agent exchange: use `skills/a2a-agent-interoperability` for applicable Strategy 2030 A2A implementation; do not confuse generic APIs, MCP tools or internal subagents with A2A or declare an unimplemented applicable requirement complete;
- HTTP/API error-to-client contract: `skills/api-error-contract-handling` only for the selected API/client error behavior;
- QA selection: choose evidence for the accepted claim: API contract, backend/runtime, web/browser, or a mix. Select existing web QA only for web claims; use the API method for relevant error contracts and focused runtime observations when required. If necessary scope or evidence remains genuinely ambiguous, ask the existing Control Director for bounded clarification, not a new Owner decision;
- bounded execution control: shared `kernel/skills/anti-loop-execution`;
- authority/dependency/exact-state Core only when the assignment needs those decisions;
- technology/QA skills only for the affected surface and only when their mandatory execution prerequisites are satisfied;
- optional patterns only after both their semantic assumptions and execution prerequisites match.

**Pre-assignment capability derivation:** mandatory actions and evidence gates from this workflow and selected skills contribute concrete capabilities to `REQUIRED_CAPABILITIES`. Examples include repository write access for mutation, `repository_local_checkout` + `shell` + language/package runtime for mandatory local commands, and `interactive_browser` or a fully provisioned `playwright_runtime` when browser evidence is mandatory.

**GitHub candidate delivery for `implement_software_change`:** a code-changing assignment MUST declare an exact `github_candidate_delivery` (repository, base branch, allowed `PULL_REQUEST`/`BRANCH` kinds). This requirement is enforced by `resolve_spawn()`. The end-to-end route must prove a genuinely available, authorized publication operation by the responsible delivery segment; a read-only Executor does not acquire push rights just because Control has a GitHub connector. For GitHub-backed code work in a connected, admitted Codex environment, default to Executor-owned native GitHub publication. Control/another admitted delivery segment may publish only when explicitly authorized and actually needed, not for Director convenience. Preserve the distinct required capabilities/evidence; do not infer `pull_request_create` or branch write from read access.

Before code edits, bind the exact responsible publisher, PR/branch kind and handoff. Reuse known current destination/publisher capability evidence within its freshness/state bounds; repeat probes, preflight/model-setting or UI confirmations only for material uncertainty or state change. Compilation/admission remain mandatory; never fabricate proof. For an authorized Codex Cloud `PULL_REQUEST` route with proven write and PR capability, ordinary delivery is code -> necessary in-scope local checks -> commit -> push -> open Draft PR (or the provider's supported native publish action), followed by the exact remote HEAD and candidate in `EXECUTOR_RESULT`. A local patch, transcript or unpushed commit is not a published candidate. Keep expressly selected `BRANCH` and separate-publisher routes only with a proven named end-to-end publication segment; an unspecified later publisher is not a route.

Freeze the durable assignment once and dispatch its link. When the authorized GitHub route is available, never send complete source files, patches, base64 or giant JSON evidence bundles through agent chat. After publication, hand off PR URL/full HEAD and concise `EXECUTOR_RESULT`/`VERIFICATION_RESULT` references. The producing role publishes its own result in the existing Issue/PR when authorized; Executor includes affected paths, necessary focused checks and evidence. Work/Chat Director and manual/native routes remain supported without a dependency on a local CLI, daemon, webhook, Actions trigger, MCP service, Workspace Agent API or observer adapter. Existing compiler/admission, `github_candidate_handoff`, `resolver_transition`, Owner/Canon, independence and merge authority remain unchanged.

Before the Verifier handoff, the candidate must be **visible on GitHub** as an open, unmerged PR (Draft is independently verifiable) or a separately permitted named branch. Ready-for-review and merge eligibility are separate Control promotion decisions. A PR description carries a separate exact line `Resolver-Assignment: <assignment_id>`. Branch-only publication uses `resolver/<assignment_id>/<name>`. Executor records `published_candidate` with exact GitHub repository, type, PR number/branch ref, and full HEAD SHA. `tools.github_candidate_handoff.check_github_candidate` must then read the real candidate afresh through a **Control-provided GitHub reader**, and `resolve_transition()` refuses to complete without this proof. A published Draft PR may proceed to independent verification after successful readback; ready-for-review and merge eligibility remain separate Control decisions.

The explicit Assignment delivery declaration controls this check. Manual Stage 1 assumes the Director supplies the intended task and checks its delivery; it does not authenticate an immutable original issuance against arbitrary edits to internal JSON. Planning, diagnosis and non-code Research reports may use the requested Issue/PR comment or durable report without a code candidate.

**Executor MUST NOT merge its own PR**, even if the credential technically permits it. Promotion/merge remains a separate authorized, verified Control transition. PR presence/technical CI PASS does not prove business/architecture acceptance. On genuine native GitHub publication failure, STOP with the exact provider error and preserve the current attempt/branch: no Control reconstruction from chat source, second Executor, fabricated Draft PR or silent publisher substitution. An explicitly selected, proven separate-publisher route remains supported for destinations that need it. If acknowledgement is unknown, reconcile the existing attempt/candidate; do not automatically repeat implementation.

**Legacy coding transport retired:** For an accepted native Codex/GitHub Assignment, use its configured repository-connected Codex Executor to publish the actual remote candidate. Linear `@codex` delegation, PR-comment `@codex address that feedback` and disconnected legacy Codex are not implementation or repair substitutes. Never accept text-only commit claims instead of PR/HEAD. A genuine native failure preserves the attempt and exact error without switching to old transport. Where Owner selected visible Desktop-integrated Codex browser MCP, do not open hidden Chrome or Work cloud browser in its place.

**Publication and partial-work checkpoint:** The assigned remote PR/branch is the one durable software handoff. Before making local changes the selected publisher must already be able to publish into it. After in-scope edits, do not end a substantive execution turn or release a disposable workspace without publishing intended changes to that remote ref and reading the resulting HEAD. Failed tests or incomplete implementation are allowed as an explicitly labeled **WIP Draft checkpoint**, not as a completed candidate. If publication genuinely fails, keep the same active attempt and return `PARTIAL/BLOCKED` with the exact error, current remote/head mismatch and unsaved-work limitation. Do not report a local commit or chat patch as published, hide the loss, start another PR/Executor or enter a speculative repair loop. Control reads back the exact GitHub candidate before moving the baton to verification or an accepted next stage.

**Work-native Executor admission:** An approved Work-hosted Software workflow may use a **distinct Work Subagent Executor** rather than Codex Cloud when the actual native task can execute the bounded assignment and publish to the authorized existing GitHub candidate. Parent Work Director remains a Director and does not perform its own microfix. Reuse valid host/tool/repository capability observations without repeating setup probes for each child; verify only changed or newly required permissions and exact publishing evidence. Keep required independent Verifier for risk-elevated claims and exact GitHub HEAD readback. The full formalized evidence inventory is not a mandatory chat report for a routine task; the applicable real compiler/admission and safety gates still control execution.

**Automatic CI/Preview boundary:** Already configured remote CI and native Preview run as `PLATFORM` behavior after publication. `CONTROL`, not the ordinary coding Executor, independently observes build/Preview status, reconciles missing evidence and decides whether a real code defect warrants a bounded repair. Executor handoff must not depend on polling CI/Preview, accessing a provider build API/dashboard or awaiting a successful automatic build. An optional provider visibility failure (including HTTP 401) is not a code failure or a stop for independent implementation. A specifically authorized deployment/provider-diagnostic task and genuinely mandatory safety validation retain their actual gates.

**Transform:** assignment → bounded plan where needed → implementation → declared technical validation through proven execution surfaces → `EXECUTOR_RESULT`.

`local/technical validation` is not an unconditional assumption that every destination has a local machine. The exact validation mode is assignment-specific:

- if acceptance requires local-worktree/runtime evidence, the assignment is admissible only on a destination that proves those local capabilities;
- if remote repository/API evidence fully satisfies the stated claim, a declared remote mode may be used;
- remote evidence must not be used to assert local branch/worktree/runtime facts;
- missing mandatory validation capability before assignment is `ASSIGNMENT_NOT_ADMISSIBLE`, not a planned downstream `BLOCKED`;
- loss of a previously proven capability during execution is `BLOCKED_RUNTIME_DRIFT`.

**Exit:** for `implement_software_change`, the selected GitHub candidate is published and a factual `EXECUTOR_RESULT` records its exact remote identity; the work product, resulting state, evidence refs/limitations/deferred findings are recorded. Final acceptance is not self-certified; route to independent verification when required, and preflight the verifier destination against its own mandatory evidence paths before assigning verification.

For substantive independent verification, prefer Medium when selectable and use a separate admitted Chat/Work instance reading the real GitHub diff at the exact full HEAD. Instantaneous capability preflight is not completed candidate review. Director does not implement; Executor never independently verifies or merges its own candidate.
